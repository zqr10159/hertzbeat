本指南说明如何将 HertzBeat 1.9.0 升级到 1.9.1。管理端、Collector 和数据库相关组件应使用同一官方 1.9.1 发行版中的配套制品。不要据此推断其他源版本或未经验证构建的兼容性。生产升级前，请等官方发行制品发布，再使用对应下载包或镜像标签。

## 快速检查

经核对，1.9.1 源码中的 H2、MySQL 和 PostgreSQL Flyway 迁移目录与正式 `v1.9.0` 相同；本次没有新增 Flyway 迁移文件。1.9.1 将管理端访问收紧为必须具有精确的 `admin` 角色，因此请在安排升级前检查账号。

1.9.1 随附的 `application.yml` 默认启用 Basic 和 JWT 认证，不启用 Digest 认证。此默认值不会改写已有配置文件。如果 Docker、Kubernetes 或安装包部署沿用旧的 `application.yml`，其中的 `sureness.auths` 列表仍然生效，可能仍包含 `digest`。

## 建议顺序与维护窗口

1. 盘点管理端、数据库、远程 Collector、自定义模板和部署专用配置。
2. 按下文检查管理员账号及认证配置。有条件时，先在预发布环境演练账号调整和配置合并。
3. 安排维护窗口，暂停 HertzBeat 写入，备份数据库及部署文件，然后升级管理端和配套 Collector。
4. 完成升级验收后，再恢复正常使用。

## 升级前备份

1. 记录当前 1.9.0 镜像摘要或安装包、启动参数、挂载路径和 Collector 版本，并保留 1.9.0 制品以便回滚。
2. 备份元数据库。复制内置 H2 数据库前先停止 HertzBeat；MySQL 或 PostgreSQL 应使用一致性备份方式。
3. 备份当前生效的 `application.yml`、`sureness.yml`、证书和密钥文件、`define/` 下的自定义文件以及 `ext-lib/` 下的自定义 JAR。此类备份可能包含凭据和私钥，请妥善保护。
4. 保存 `compose.yaml`、`.env`、启动参数、Kubernetes 清单、ConfigMap 和 Secret 等部署文件。不要把密钥值写入工单或日志。
5. 准备完整的 1.9.1 管理端及配套 Collector 制品。只替换主 JAR 不构成升级：应使用完整官方镜像，或替换完整安装包，包括 `lib/`。

## 升级 Docker 部署

修改 Compose 前，先检查当前容器的挂载和镜像引用。保留现有数据及配置挂载，不要执行 `docker compose down -v`。

对于 Compose 部署，待官方发布 1.9.1 后，仅将 HertzBeat 镜像更新为对应官方镜像。保留已有卷、环境变量、端口和密钥引用，然后重建服务：

```bash
docker compose config
docker compose pull hertzbeat
docker compose up -d hertzbeat
docker compose logs --follow hertzbeat
```

直接运行容器时，拉取官方 1.9.1 镜像，停止并移除旧容器，但不要删除其卷；随后使用相同且已复核的挂载、环境变量、端口和网络设置启动新镜像。保留旧镜像引用或摘要以便回滚。远程 Collector 应使用同一发行版的 1.9.1 制品升级，并保留原有且已复核的配置。

未经检查不要把旧 `application.yml` 覆盖到镜像配置上。如果该文件通过挂载使用，请参阅下文“认证与 Digest”，决定是否移除现有 `digest` 条目。除非另有明确审核的变更，只调整这一项时请保留 `sureness.auths` 中其余认证方式和所有密钥。

## 升级安装包部署

以下命令以 `/opt/hertzbeat` 为例，请替换成实际安装路径。使用部署当前支持的停止命令，并确认管理端已停止后再操作文件。

```bash
cd /opt/hertzbeat-1.9.0
./bin/shutdown.sh
```

将经过核验的 1.9.1 压缩包解压到新的暂存目录。检查其中的 `config/` 文件，再把部署专用设置和密钥合并进去。保留已停止服务的 H2 `data/` 目录，或确保新实例可访问已备份的外部数据库。将复核过的自定义模板和 JAR 放入对应的 `define/`、`ext-lib/` 目录。不要把旧版 `bin/` 或 `lib/` 复制进新安装目录，也不要只替换主 JAR。切换到完整的 1.9.1 安装包后，使用包内脚本启动：

```bash
cd /opt/hertzbeat-1.9.1
./bin/startup.sh
```

检查启动日志后，再从同一官方发行版升级远程 Collector。验收完成前保留原 1.9.0 目录，不要覆盖。

## 检查管理端账号

1.9.1 的管理界面和 API 仅允许具有精确 `admin` 角色的账号访问。升级前检查当前生效的 `sureness.yml`，确认哪些人员可信且获准管理整个 HertzBeat 实例。仅为这些获准账号手动授予 `admin`，并保留各账号原有标识和凭据。不要将所有 `user`、`guest`、自定义角色、服务账号或 Collector 账号一概提升权限；系统不会自动提升任何账号。

旧 token 无法绕过服务端角色校验，也不会因此获得 `admin` 权限。自定义路由规则或排除路径不能恢复非管理员账号的管理权限。修改账号后重启管理端，使用获准的管理员重新登录；客户端需要时签发新 token，并按常规凭据流程撤销旧 token。确认非管理员用户和自动化身份仅保留所需权限。

以 1.9.1 的 `sureness.yml` 为基础，只合并已审核的账号修改。不要用旧版整份文件覆盖新版路由规则。

## 认证与 Digest

1.9.1 随附的 `application.yml` 通过 `sureness.auths` 使用 `basic` 和 `jwt`，默认不启用 Digest。替换镜像或安装包不会编辑已挂载或保留的 `application.yml`。请检查管理端实际挂载并读取的配置文件。

如果希望使用随附的 Basic 和 JWT 认证且不启用 Digest，请确认生效配置的列表为：

```yaml
sureness:
  auths: [basic, jwt]
```

如果旧列表包含 `digest`，且你的策略是关闭 Digest，只删除这一项。保留部署仍需的其他认证方式、`sureness.jwt.secret` 及其余现有设置。如需明确启用 Digest，则在保留其他必要认证方式的同时，将 `digest` 加入现有列表，例如：

```yaml
sureness:
  auths: [basic, jwt, digest]
```

修改实际生效的配置后重启管理端。使用受保护的端点和符合策略的账号验证行为。只有启用了 Digest 且命中的路由要求认证时，才应出现 `WWW-Authenticate: Digest` challenge；公开路由没有 challenge 并不能证明 Digest 已关闭。

Digest 是 HTTP 摘要质询响应认证，不是对密码或网络流量的加密。传输保密性应使用 TLS。只保留部署所需的认证方式；遇到登录问题时，不要因此放宽其他路由或授权规则。

## 升级并验证 Collector

管理端和远程 Collector 应从同一官方 1.9.1 发行制品集升级。确认每个 Collector 重新连接，检查其日志，并验证一个有代表性的监控对象收到新采集数据。重启前复核自定义 Collector 设置及 `ext-lib/` 依赖。

端口 `1158` 用于管理端与 Collector 之间的传输。只允许可信且确实需要连接的 Collector 来源网络访问该端口。管理账号变更不会修改或修复现有 Collector 传输协议的认证机制。

## 升级验收

恢复正常使用前，请确认：

- 管理端运行预期的 1.9.1 构建，且没有数据库或配置错误。
- 获准管理员可以登录并使用管理功能；没有精确 `admin` 角色的账号会被拒绝。
- 认证行为符合复核过的 `sureness.auths` 列表，包括预期的 Digest 状态。
- 远程 Collector 已重新连接，且有代表性的监控对象收到新数据。
- 数据库连接、自定义模板、密钥和 `ext-lib/` 依赖均符合已复核的部署配置。

## 安全回滚

若验收失败，停止 1.9.1 管理端和受影响的 Collector。恢复完整的 1.9.0 镜像或安装包，以及对应的配置、部署文件、自定义模板和 `ext-lib/` 备份。如果 1.9.1 运行期间写入过数据库，应先恢复升级前的一致性数据库备份，再启动 1.9.0。不要只替换一个 JAR 来回滚，也不要假定 1.9.1 写入的数据兼容所有更早版本。升级或回滚验证完成前请保留备份。
