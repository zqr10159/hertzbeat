This guide covers an upgrade from a released HertzBeat 1.9.0 deployment to 1.9.1. It does not establish compatibility for other source versions or unverified package combinations. Before starting, confirm the 1.9.1 artifacts are available through the official Apache release channels and use the matching package or image for your deployment.

## What changes in 1.9.1

The H2, MySQL, and PostgreSQL Flyway migration directories are identical to the formal `v1.9.0` release. There are no new Flyway migration files in 1.9.1. The 1.9.1 management access policy does require a manual account review; see [admin-only access migration](../help/admin_only_migration).

The shipped `application.yml` disables Digest authentication by default. If you keep an existing or mounted `application.yml`, its `sureness.auths` setting is retained. A previous `digest` entry is not removed when you replace an image or package, so check the active file explicitly.

## Back up and stage

Before the maintenance window:

1. Record the running manager, Collector, database, and deployment versions and preserve the exact 1.9.0 package or image references for rollback.
2. Back up the metadata database. Stop HertzBeat before copying an H2 database; use a consistent backup method for MySQL or PostgreSQL.
3. Back up `application.yml`, `sureness.yml`, mounted configuration, certificates and secret files, custom templates under `define/`, and every custom JAR in `ext-lib/`. Also preserve your Compose files, `.env`, Kubernetes manifests, ConfigMaps, and Secrets as applicable.
4. Stage the complete matching 1.9.1 manager package or image. Do not replace only the main JAR. If you run remote Collectors, stage the 1.9.1 Collector artifact from the same release as well; do not mix unverified builds.

## Migrate configuration and accounts

Use the 1.9.1 configuration as a reference, then merge your deployment-specific settings into it. Preserve your database credentials, `sureness.jwt.secret`, TLS private keys, and other secrets. Do not overwrite a mounted production file with a sample configuration. Keep custom templates and `ext-lib/` contents in the deployment unless you have separately reviewed a change to them.

Management API and UI access requires the exact `admin` role in 1.9.1. Inventory user, guest, custom, and automation accounts before upgrading. Manually assign `admin` only to people trusted to administer the whole instance. No account is automatically promoted. Existing tokens do not bypass the admin-only backend check, and a management role or excluded-route setting cannot restore access to a non-admin account. Follow the [admin-only migration steps](../help/admin_only_migration) and rehearse them with your own account configuration.

The 1.9.1 Digest default applies to its shipped configuration. If your deployment reuses an older `application.yml`, inspect `sureness.auths` and remove `digest` only if that is your intended policy. Restart after changing the active configuration.

## Upgrade and verify Collectors

Upgrade manager and Collector artifacts only from the same verified 1.9.1 release set. After startup, confirm each remote Collector is connected in HertzBeat, inspect its logs, and verify that a known monitor receives fresh collection data. Recheck custom Collector configuration and mounted `ext-lib/` dependencies.

Port `1158` carries manager-to-Collector transport. Limit inbound access to the trusted Collector source networks that need it. The 1.9.1 management API migration does not change or repair authentication for the existing Collector transport protocol.

## Acceptance checks

Before resuming normal traffic, verify:

- The manager reports the expected 1.9.1 build and starts without database or configuration errors.
- A trusted administrator can sign in and use the management API; an account without the exact `admin` role is denied.
- Each remote Collector reconnects and a representative monitor produces fresh data.
- The active `application.yml`, `sureness.yml`, custom templates, secrets, and `ext-lib/` match the reviewed deployment configuration.
- Authentication behavior matches the active `sureness.auths` list, including whether Digest is intentionally enabled.

## Roll back safely

If acceptance checks fail, stop HertzBeat and the affected Collectors. Restore the complete saved 1.9.0 package or image and the matching configuration, templates, and `ext-lib/` backup. If the database was written during the 1.9.1 run, restore the consistent pre-upgrade database backup before starting 1.9.0. Do not roll back by replacing only a JAR or by assuming that data written by 1.9.1 is compatible with every earlier build. Keep the 1.9.1 backups until the upgrade has been accepted.
