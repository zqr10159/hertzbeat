## HertzBeat 1.9.1 Upgrade Guide

This guide describes the upgrade path from HertzBeat 1.9.0 to 1.9.1. Use the matching manager, Collector, and database artifacts from the same official 1.9.1 release. Do not infer compatibility for other source versions or unverified builds. Wait until the official release artifacts are published before using their download links or image tags in production.

## Quick check

The H2, MySQL, and PostgreSQL Flyway migration directories in the verified 1.9.1 source are identical to formal `v1.9.0`; this release adds no Flyway migration files. 1.9.1 does tighten management access to accounts with the exact `admin` role, so review accounts before scheduling the upgrade.

The shipped `application.yml` enables Basic and JWT authentication and leaves Digest authentication disabled. This default does not rewrite an existing configuration file. If Docker, Kubernetes, or an installation reuses an older `application.yml`, its `sureness.auths` list remains active and may still contain `digest`.

## Recommended order and maintenance window

1. Inventory the manager, database, remote Collectors, custom templates, and deployment-specific configuration.
2. Review administrator accounts and authentication settings below. Test the account changes and configuration merge in a staging deployment when available.
3. Schedule a maintenance window. Stop writes to HertzBeat, back up the database and deployment files, then upgrade the manager and matching Collectors.
4. Run the acceptance checks before returning the service to normal use.

## Back up before upgrading

1. Record the exact 1.9.0 image digest or package archive, runtime arguments, mounted paths, and Collector versions. Keep the 1.9.0 artifacts available for rollback.
2. Back up the metadata database. Stop HertzBeat before copying an embedded H2 database. Use a consistent backup procedure for MySQL or PostgreSQL.
3. Back up the active `application.yml`, `sureness.yml`, certificates, secret files, custom files under `define/`, and custom JARs under `ext-lib/`. Protect these backups because they can contain credentials and private keys.
4. Save deployment files such as `compose.yaml`, `.env`, startup arguments, Kubernetes manifests, ConfigMaps, and Secrets. Do not include secret values in tickets or logs.
5. Stage the complete 1.9.1 manager and matching Collector artifacts. A manager-only JAR replacement is not an upgrade: use the complete official image or replace the complete installation package, including `lib/`.

## Upgrade Docker deployments

Check the current container mounts and image reference before changing Compose. Keep the existing data and configuration mounts, and do not use `docker compose down -v`.

For Compose, update only the HertzBeat image to `apache/hertzbeat:1.9.1` after that official image is published. Keep your existing volumes, environment, ports, and secret references. Then recreate the service:

```bash
docker compose config
docker compose pull hertzbeat
docker compose up -d hertzbeat
docker compose logs --follow hertzbeat
```

If you run the container directly, first record its mounts and volume names with `docker inspect hertzbeat`, then pull the official image, stop and remove the old container without deleting its volumes, and rerun your saved `docker run` command with the image changed to `apache/hertzbeat:1.9.1`. Reattach any anonymous volume by its recorded volume name; repeating an anonymous `-v /container/path` alone creates a new empty volume. Preserve the reviewed mounts, environment, ports, and network settings, and keep the old image reference or digest for rollback. For example:

```bash
docker pull apache/hertzbeat:1.9.1
docker stop hertzbeat
docker rm hertzbeat
# Rerun your saved docker run command, replacing only its image with apache/hertzbeat:1.9.1.
```

Do not add `-v` to `docker rm`. Upgrade remote Collectors from the matching 1.9.1 release artifacts and retain their existing reviewed configuration.

Do not copy an old `application.yml` over the image configuration without reviewing it. If it is mounted, follow “Authentication and Digest” below to decide whether to keep or remove its existing `digest` entry. Keep the rest of the `sureness.auths` methods and all secrets unchanged unless you have separately approved a specific change.

## Upgrade installation packages

The examples use `/opt/hertzbeat`; substitute your installation path. Run the shutdown command supported by your deployment and confirm the manager has stopped before touching its files.

```bash
cd /opt/hertzbeat-1.9.0
./bin/shutdown.sh
```

Extract the verified 1.9.1 archive into a new staging directory such as `/opt/hertzbeat-1.9.1`. Review its `config/` files, then merge only your deployment-specific settings and secrets. For embedded H2, copy the stopped `data/` directory into the new installation; for an external database, restore access to the backed-up database.

Copy reviewed custom templates and JARs into the corresponding `define/` and `ext-lib/` locations. Do not copy the old `bin/` or `lib/` directories into the new installation, and do not replace only the main JAR. Switch to the complete 1.9.1 package and start it using its supplied scripts:

```bash
cd /opt/hertzbeat-1.9.1
./bin/startup.sh
```

Check the startup logs before upgrading remote Collectors from the same official release. Keep the original 1.9.0 directory untouched until acceptance is complete.

## Review management accounts

In 1.9.1, management UI and API access requires the exact `admin` role. Before upgrading, inspect the accounts in your active `sureness.yml` and identify the people who are trusted to administer the whole HertzBeat instance. Manually grant `admin` only to those approved accounts, preserving each account's existing identifier and credential. Do not promote every `user`, `guest`, custom-role, service, or Collector account. No account is promoted automatically.

An old token does not bypass the server-side role check and does not gain `admin` privileges. Custom route rules or excluded paths do not restore management access to a non-admin account. After changing accounts, restart the manager, sign in again with an approved administrator, and issue replacement tokens where your clients require them. Revoke old tokens according to your normal credential process. Check that non-admin users and automation identities retain only the access they need.

Start with the 1.9.1 `sureness.yml` and merge only the account edits you reviewed. Do not overwrite the new route rules with an older whole-file copy.

## Authentication and Digest

The 1.9.1 shipped `application.yml` uses `sureness.auths` with `basic` and `jwt`; Digest is not enabled by default. Replacing an image or installation package does not edit a mounted or preserved `application.yml`. Inspect the configuration file actually mounted by the running manager.

If you intend to use the shipped Basic and JWT methods without Digest, make sure the active list is:

```yaml
sureness:
  auths: [basic, jwt]
```

If the existing list contains `digest`, remove only that entry when that is your intended policy. Preserve any other authentication methods your deployment requires, along with `sureness.jwt.secret` and the rest of your existing settings. To intentionally enable Digest, add `digest` to the existing list while retaining the other required methods; for example:

```yaml
sureness:
  auths: [basic, jwt, digest]
```

Restart the manager after editing the active configuration. Verify the behavior using a protected endpoint and the account type expected by your policy. A `WWW-Authenticate: Digest` challenge is expected only when Digest is enabled and the matched route requires authentication; its absence on a public route does not prove Digest is disabled.

Digest is HTTP challenge-response authentication, not encryption of passwords or network traffic. Use TLS for confidentiality in transit. Keep only the authentication methods your deployment needs and do not weaken unrelated route or authorization rules to address a login problem.

## Upgrade and verify Collectors

Upgrade the manager and remote Collectors from the same official 1.9.1 release set. Confirm each Collector reconnects, inspect its logs, and verify that a representative monitor receives fresh data. Review custom Collector settings and dependencies in `ext-lib/` before restarting them.

Port `1158` carries manager-to-Collector transport. Limit inbound access to the trusted Collector networks that need it. The management account change does not change or repair authentication for the existing Collector transport protocol.

## Acceptance checks

Before resuming normal use, confirm:

- The manager starts with the expected 1.9.1 build and reports no database or configuration errors.
- An approved administrator can sign in and use management functions; an account without the exact `admin` role is denied.
- Authentication matches the reviewed active `sureness.auths` list, including the intended Digest behavior.
- Remote Collectors reconnect and a representative monitor receives fresh data.
- Database connectivity, custom templates, secrets, and `ext-lib/` dependencies match the reviewed deployment.

## Roll back safely

If acceptance fails, stop the 1.9.1 manager and affected Collectors. Restore the complete saved 1.9.0 image or installation package, its matching configuration and deployment files, and the saved custom templates and `ext-lib/` contents. If 1.9.1 wrote to the database, restore the consistent pre-upgrade database backup before restarting 1.9.0. Do not roll back by swapping only a JAR or assume that data written by 1.9.1 is compatible with every earlier build. Keep the backups until the rollback or upgrade has been verified.
